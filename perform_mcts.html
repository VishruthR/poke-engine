perform_mcts in poke-engine

Source: src/mcts.rs:241

perform_mcts runs a Monte Carlo Tree Search over the current battle State and returns per-move visit/score statistics for both sides. Each iteration walks the standard MCTS loop: selection → expansion → rollout → backpropagation. Because Pokémon is a simultaneous-move, stochastic game, the tree stores moves and visit stats independently for side 1 and side 2 at every node.

Setup

  1. Create a root Node, populate it with the legal move lists for both sides, mark it as root.
  2. Evaluate the starting state once (root_eval); rollouts are scored relative to this baseline via a sigmoid.
  3. Loop in batches of 1000 iterations until max_time elapses, or hard-stop at 10,000,000 visits (f32 precision degrades beyond that).

One iteration: do_mcts

fn do_mcts(root, state, root_eval) {
    (leaf, s1_move, s2_move) = root.selection(state);
    new_node              = leaf.expand(state, s1_move, s2_move);
    score                 = new_node.rollout(state, root_eval);
    new_node.backpropagate(score, state);
}

1. Selection

Descend from the root. At each node, pick the s1 move and s2 move that independently maximize UCB1 (avg_score + sqrt(2·ln(parent_visits) / visits), infinity if unvisited). Look up the child bucket for that (s1, s2) pair. Because move interactions in Pokémon are stochastic, each bucket is a vector of child nodes — one per possible outcome — so sample one weighted by its instructions.percentage, apply those instructions to the state, and recurse. Stop when a (s1, s2) pair has no children yet.

2. Expansion

Call generate_instructions_from_move_pair to produce all stochastic outcomes of the chosen move pair. Build a child Node for each, store the vector under (s1_move, s2_move), and sample one outcome (again weighted by probability) to roll out from. Damage rolls are only branched at depth 0–1 (should_branch_on_damage) to keep the tree tractable.

3. Rollout

No random playout — poke-engine uses a heuristic evaluation instead. If the battle is over, return the terminal value (0 for loss, the win value otherwise). Otherwise call evaluate(state) and squash the delta against the root via sigmoid(eval − root_eval), yielding a score in (0, 1) from side 1's perspective.

4. Backpropagation

Walk back to the root. At each step, credit the parent's MoveNode entries: s1's chosen move gets +score, s2's chosen move gets +(1 − score) (zero-sum). Reverse the stored instructions on the State as you go, so the mutable state returns to the root position by the end of the iteration.

Result

After the time budget expires, perform_mcts packages the root's s1_options and s2_options into an MctsResult containing each move's total score and visit count, plus the total iteration count. The caller (typically the PyO3 wrapper mcts in poke-engine-py/src/lib.rs) picks the move with the most visits as the recommended action.

Notable design choices

  • Decoupled per-side stats: simultaneous moves are handled by storing independent UCB stats for s1 and s2 at each node, rather than minimax-style alternation.
  • Stochastic children as vectors: each (s1, s2) bucket is a list of outcomes sampled by probability — both during selection (revisiting) and expansion (first visit).
  • Heuristic leaves, not playouts: rollouts are sigmoid(evaluate(state) − root_eval), trading variance for speed and domain knowledge.
  • Reversible state: instructions are applied on the way down and reversed on the way up, so the search runs against a single mutable State.
  • Raw pointers + unsafe: parent/child links use *mut Node to sidestep Rust's borrow checker during recursive mutation.
